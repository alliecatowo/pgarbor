## 2. Are PostgreSQL's native suites being run against both engines?

**No demonstrated two-engine native-suite campaign exists.** Distinguish (a) doc/command-derived YAML cases recorded against PG18, (b) parsing official PostgreSQL suites, (c) executing those suites, and (d) invoking PostgreSQL's own runner binaries. These are four different claims.

The repository has adapters for (b)/(c). It does **not** invoke upstream `pg_regress` or upstream `isolationtester`: regress is Python scheduling + psql, and isolation is a Python scheduler/printer/wait detector (`harness/pgarbor_harness/regress/runner.py:1`; `isolation/tester.py:5`). Paths default to the local upstream source tree, overridable with `PGARBOR_PG_SOURCE` (`config.py:182`). Local source `/home/allie/develop/reference/postgres-18/configure.ac:20` declares 18.6, but generated `src/include/pg_config.h` is absent; future evidence must pin source hashes rather than relying on a directory named postgres-18.

**The PGArbor target is wired, not missing.** `PgarborCommand` defaults to `target/release/pgarbor create FILE`, then `serve FILE --host HOST --port PORT --branch main` (`runner/targets.py:293`). Provision creates a fresh file and process (`:378`); readiness requires real `SELECT 1` (`:151`, `:203`); restart/release/liveness/log collection exist. CLI maps `--target pgarbor --binary PATH` into it (`cli.py:322`); regress uses `_live` (`:625`), isolation uses `_make_target` (`:645`). Factory campaign phases also call both adapters against PGArbor (`harness/pgarbor_factory/campaign.py:439`, `:479`). Thus adding another nominal target enum is not the needed work.

Actual blockers and missing integration:

1. **Executable SQL path:** implement Database create/open/bootstrap/session, simple/extended query dispatch and a live listener. `Database` entry points return API-04 0A000 (`crates/pgarbor/src/database.rs:102`); simple query returns API-07 (`simple_query.rs:43`). Compiling the binary or its argument parser does not satisfy `PgarborTarget` readiness. CLI create alias/serve host/port flags already match templates (`crates/pgarbor-cli/src/cli.rs:77`, `:142`); do not diagnose a flag mismatch without a real smoke probe.
2. **Regression database contract mismatch:** runner unconditionally connects tests to `regression` (`regress/runner.py:66`, `:187`) and normally DROP/CREATE DATABASE TEMPLATE=template0 plus ALTER DATABASE settings (`:306`). PGArbor v1 has one logical database per branch; CREATE DATABASE is 0A000 (`contracts/crates/pgarbor.md:68`, `:85`). `--use-existing` skips setup but still uses the hard-coded regression name, ignoring the provisioned endpoint's `postgres`. Add explicit database-name/setup policy and correct session environment, or deliberately support a regression database alias under an amendment. Do not turn unsupported CREATE DATABASE into successful no-op SQL. Even after adapter provisioning is fixed, upstream tests that exercise multiple databases remain real UNSUPPORTED results.
3. **PG18 suite environment:** default OracleContainer has **no mounts** (`oracle/container.py:96`, `:135`), while psql mounts source/output paths in its client container (`regress/psql.py:94`). The same module claims the server has those mounts (`:21`), but regress CLI uses plain `OracleContainer().ensure()` (`cli.py:613`; `_live` at `:355`). Construct and validate suite-specific server mounts using `regress_mounts` (`oracle/container.py:116`), including writable output/tablespace paths, permissions and stable paths for server-side COPY. Do this in the harness-owned container, not by silently altering the developer oracle.
4. **Missing native test support library:** regress documents that `regress.so` does not exist (`regress/psql.py:17`; `regress/manifest.py:24`). Matching PG errors caused by missing fixtures can produce a differential PASS without testing the feature. A controlled PG18 environment needs the matching compiled test support library and paths, or explicit environment-blocked counts. PGArbor cannot load PostgreSQL C extensions by pretending success; affected cases must retain unsupported/block reasons. Preserve official and differential verdicts separately.
5. **Trustworthy isolation wait detection:** sessions call `pg_backend_pid()` and `pg_catalog.pg_isolation_test_session_is_blocked(...)` (`isolation/tester.py:277`, `:303`). Current native regress also depends on psql meta-commands. A direct Rust API test can exercise the embedded engine now that its methods become implemented; it cannot be pointed at by a DSN. An embedded corpus backend would need a statement/session executor adapter or a dedicated bridge. Native psql tests still need wire; use API tests as a complementary layer.
7. **Suite selection/reporting:** counts already exist in CLI JSON (`cli.py:631`, `:652`), per-test regress summary (`regress/runner.py:281`), factory family evidence (`campaign.py:468`). Missing work is validated invocation, full denominator/provenance, differential counts in CLI, fail-closed gates, and actual retained two-target results—not inventing an entirely new counter system.

## 3. Robustness and false-PASS risks

### Confirmed high-priority weaknesses

1. **OID normalization masks wrong literals/data.** All oid-typed values >=16384 are independently canonicalized (`compare/normalize.py:121`, `:153`, `:173`). `SELECT 20000::oid` vs 30000 passes, reproduced in prior review (`runs/review/codex-review-01.md:19`). Provenance is needed to distinguish allocated object identity from literal/stored OID data. Default user-OID remapping also hides a wrong user type if its identity is never independently anchored. Preserve built-in OIDs exactly. Add positive allocation-renumbering controls and negative literal/identity mutants; policy change requires amendment/reviewed rerecording.
2. **Opt-in masks are column/type-wide.** `timestamps` masks every non-null date/time column in a step, including deterministic arithmetic beside now() (`normalize.py:199`, `:221`). UUID/XID/LSN/PID masks have analogous scope (`:225`, `:229`, `:251`). This can hide bad dates, repeated “random” constants or wrong IDs. Test deterministic adjacent columns and restrict masks by recorded expression/column provenance. EXPLAIN masking correctly retains ANALYZE actual row counts (`normalize.py:94`); retain a mutant proving this.
3. **Failed setup can bless the wrong feature test.** Recorder checks intent only for case steps (`oracle/recorder.py:157`), and setup faults exclude SQL ERROR results (`:187`). Prior review reproduced setup 42601 followed by expected 42P01 being accepted (`runs/review/codex-review-01.md:20`). This audit scanned every current expected transcript: **zero recorded setup SQL-error cases found**. The implementation hole is real, but do not claim the current corpus is already contaminated. Public `record_case` also bypasses the gate/live fingerprint used by `record_corpus` (`recorder.py:270`, `:323`).
4. **Reproduced stale regress result false PASS.** `run_psql` reuses `out_dir/results/<test>.out` without removing it before launching Podman (`regress/psql.py:130`). `_judge` checks timeout/connection/corruption text, then compares the file without rejecting launcher failures (`regress/runner.py:205`, `:216`). Audit probe supplied a retained matching output and `PsqlRun(exit_code=125, stderr='podman failed')`: **official=PASS, differential=PASS**. A real Podman startup failure before the shell truncates the file can take that path when an output directory is reused. Require a fresh output artifact and distinguish launcher/transport failures from expected SQL errors; regress legitimately allows SQL errors in output (`psql.py:35`).
5. **Apps are disconnected; naïve reconnection could falsely pass.** Campaign scans absent `harness/fixtures`, supplies `PGARBOR_DSN`, parses JSON lines beginning `{` with per-test `test/status` fields, and accepts exit 0 with no parsed results (`pgarbor_factory/campaign.py:541`, `:560`, `:585`, `:599`). Actual apps use `tests/apps`, `DATABASE_URL`, and prefixed aggregate `FIXTURE_RESULT` (`tests/apps/node-pg/run.sh:6`, `:33`; Prisma `run.sh:34`; sqlx `src/main.rs:400`). Audit probe: `_parse_client_lines` returns `[]` for a valid real fixture summary. At present discovery yields BLOCKED; fixing discovery alone leaves weak result validation. Reject absent/malformed/duplicate summaries, zero substantive tests, count inconsistencies and nonzero exit, even if stdout claims success.
6. **Reproduced zero-work SLT PASS.** `run` starts with PASS (`sqllogictest/runner.py:334`), `halt` immediately breaks (`:297`), and no minimum execution count is enforced. With only Session connect/close mocked, a file containing `halt` returned **PASS, records_passed=0**. Empty/early-halt/empty-tree selections must not be engine coverage passes. SLT also deliberately compares query column count and rendered values rather than type OIDs (`:277`), so it cannot replace typed differential tests.

### Important safeguards and limits

- **Multiset is a Counter, not a set:** row multiplicity is preserved (`compare/typed.py:136`). Automatic order uses a lexical top-level ORDER BY decision (`:88`); explicit multiset overrides even ordered SQL (`:115`). This is appropriate for genuinely unordered SQL, but wrong explicit annotations or parser mistakes can hide order bugs. Test comments/CTEs/subqueries/multiple statements/prepared execution and explicit-order misuse. LIMIT without ORDER BY has genuinely unspecified membership; recorder instability is coverage loss rather than evidence PGArbor is wrong.
- **Recorder determinism happens after normalization but before unordered comparison:** it compares canonical transcript JSON directly (`oracle/recorder.py:235`). Legitimate row permutation can reject a case as nondeterministic; overbroad normalization can instead mask a reference bug. Always publish nondeterministic/quarantine/missing counts. Latest recorder status and current quarantine inventory differ materially from `STATUS.md:44`'s older 7+7 snapshot.
- **Quarantine/reference gaps do not individually PASS:** differential quarantine returns INVALID_CASE; missing/hash-stale refs return BLOCKED (`runner/differential.py:110`). SLT skipped records turn otherwise-passing files BLOCKED (`sqllogictest/runner.py:113`); isolation heuristic waits never PASS (`isolation/tester.py:642`). Preserve these rules and display the entire selected/cataloged denominator. Forty quarantines are not forty successes, and 5,790 reference files are not engine passes.
- **Shell exit code is not a verification gate:** `diff` deliberately returns 0 for mismatches/unsupported/blocked and most mixed failures (`cli.py:533`, `:543`); regress and isolation also unconditionally return 0 after output (`:637`, `:661`). Empty selections can therefore look green; isolation silently filters unknown `--only` names (`isolation/tester.py:659`), unlike regress which rejects unknown names (`regress/runner.py:150`). Add strict gate mode or gate the JSON counters and completeness; retain machine-consumer compatibility by amendment if required.
- **Reference identity check is optional on ordinary diff:** CLI passes `live_reference=None` (`cli.py:533`); saved case hashes are checked, but live oracle identity matching runs only when supplied (`runner/differential.py:123`). Factory tries to supply it and explicitly notes when unavailable (`campaign.py:431`). Gate campaigns on trusted pinned provenance rather than assuming any expected file is authoritative.
- **Native output matching is intentionally narrow:** regress/isolation use byte equality after CRLF normalization and official expected variants (`regress/outdiff.py:98`). This is stronger than broad transcript masks, but neither validates the Python runner against upstream binaries. PG-environment failures copied into baselines are not positive feature coverage (`regress/runner.py:229`, `:293`). Missing regress.so, broken COPY paths, setup failures and test-prerequisite failures need environment-invalid attribution rather than being silently credited as SQL support.
- **Wire replay has independent normalization:** masks BackendKeyData and C error source fields and canonicalizes RowDescription OIDs (`wire_transcripts/replay.py:169`); keeps DataRow bytes and most statuses exact. Empty connection sets are INVALID_CASE (`:524`), a useful safeguard. Need mutants for wrong status/tag/data, extra/missing messages, user-type identity and duplicate startup parameters; startup status order is deliberately relaxed (`:29`). No checked-in real transcript currently exercises these safeguards.
- **Selftest is useful but scoped:** six hand-built transcript fixtures (`selftest/run.py:135`) cover duplicates/NULL/empty/types/errors/tags/status/notices, 18 observation mutants and five weakened comparators (`selftest/mutants.py:63`, `:85`). Audit: **36 checks, all passing**. It does not kill numeric OID-literal changes, overly masked adjacent deterministic values, failed setup, stale regress artifacts, missing app summaries or zero-work suites. Live PG-vs-PG pytest selects only the smoke family (`harness/tests/test_har_28.py:74`). Factory guard enforces the offline selftest (`pgarbor_factory/guard.py:285`, `:298`); “selftest passed” is not a blanket certification of all runners.
- **Component tests can agree with a wrong model:** FaultVfs has explicit limits—single crash and no real filesystem power cuts (`contracts/crates/pgarbor-fault.md:58`); many branch tests use SyncMode::Off (`br-10.rs:1`). A SIGKILL test is useful process recovery evidence but not a power-loss/fsync proof. Doctests/heavy properties ignored by default must be reported separately. Real bugs survived existing unit suites (review-01 findings); testing more helper functions alone will not close integration gaps.
